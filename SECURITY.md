# VENDO — безопасность

## Аутентификация

- Пароли: scrypt (N=2^15, r=8, p=1), соль на пароль; сравнение `timingSafeEqual`; для несуществующих логинов — проверка с фиктивным хешем (одинаковое время ответа).
- Сессии: 32 случайных байта в cookie `vendo_session` (`HttpOnly`, `SameSite=Lax`, `Secure` в продакшене); в БД — только SHA-256. Блокировка, смена роли и сброс пароля завершают все сессии.
- Лимиты: вход — 20/15 мин на IP и 10/15 мин на аккаунт; регистрация — 5/час на IP; восстановление — 5/час.
- Регистрация защищена honeypot-полем.
- Редирект после входа — только на относительные пути (нет open redirect).

## Первый Super Admin

Публичной регистрации администраторов нет, пароля по умолчанию в коде нет. Единственный путь — CLI с переменными окружения:

```bash
ADMIN_USERNAME=<логин> ADMIN_PASSWORD=<пароль> npm run admin:create
```

Скрипт создаёт или сбрасывает пароль Super Admin и пишет запись в журнал. Пароль нигде не сохраняется, кроме хеша в БД.

## Авторизация

- Роли: `super_admin`, `admin`, `moderator`, `support`, `seller`, `user`; матрица прав — `src/server/auth/permissions.ts`.
- Роль всегда читается из БД по сессии; данные о роли от браузера не принимаются.
- Каждый Server Action админки вызывает `requirePermission(...)`; сервисы повторно проверяют права и иерархию (нельзя менять себя и равных/старших; только Super Admin назначает администраторов).
- `/admin` отвечает 404 пользователям без права доступа.
- Объекты пользователя (объявления, фото, заявки) проверяются на владельца; чужой объект выглядит как «не найден».

## Данные и ввод

- Все входные данные валидируются zod/сервисами на сервере; SQL — только параметризованный (Drizzle).
- React экранирует вывод; тексты страниц из админки рендерятся без HTML (собственный безопасный разбор). JSON-LD экранирует `<`.
- Телефон/Telegram хранятся нормализованными; ссылки строятся только как `tel:` и `https://t.me/`. Рекламные ссылки — только `https://`.
- Изображения: проверка декодированием (MIME не доверяется), лимиты размера и пикселей, перекодирование в WebP с удалением EXIF/GPS. Отдача с `nosniff` и `sandbox` CSP.
- Публичный профиль не показывает телефон без `show_phone`; скрытый телефон объявления — только по клику и с лимитом частоты.
- Логи не содержат паролей, токенов и контактов; в аудит пишутся только идентификаторы и причины.
- IP не хранится: для лимитов используется HMAC(IP, `APP_SECRET`).

## Инфраструктура

- Секреты только в переменных окружения (`.env.local` в `.gitignore`). `SUPABASE_SERVICE_ROLE_KEY` используется только на сервере.
- RLS включён на всех таблицах без политик (миграция `0002`): роли `anon`/`authenticated` Supabase не получают доступа через REST API. Приложение подключается как владелец таблиц с сервера.
- Заголовки: `X-Frame-Options: DENY`, `nosniff`, `Referrer-Policy`, `Permissions-Policy`; приватные зоны — `noindex` и `no-store`.
- Server Actions защищены проверкой Origin (встроено в Next.js); загрузка фото — явная проверка Origin.
- `/api/cron/maintenance` требует `Authorization: Bearer $CRON_SECRET` и выключен без него.

## Известные ограничения

- Нет 2FA и подтверждения email (запланировано).
- Без SMTP/Resend восстановление пароля в продакшене не отправляет письма — нужен `MAIL_DRIVER=resend`.
- CSP для страниц не задан строго (Next.js inline-скрипты) — рекомендуется добавить nonce-CSP перед публичным запуском.
